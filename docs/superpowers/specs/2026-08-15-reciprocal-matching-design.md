# 상호 매칭 — 점수·데이터·화면 설계

작성일: 2026-08-15
상태: 설계 확정 (화면 시안까지 완료, 구현 전)
범위: 서브시스템 4의 매칭 부분 개편 — 상호 적합도 점수, 추가 필드, 데이터 축적 레이어, 운영자 화면. DM 발송은 범위 밖.

## 1. 배경

매칭은 이미 shipped다. `filterCandidates`(하드필터) → `rankMatches`(LLM 1회) → `MatchRun`/`MatchSuggestion` → 수락 시 `DeliveryItem` 2건. 이 문서는 새로 만드는 것이 아니라 **고치는** 것이다.

고치는 이유는 하나다. 지금 구조는 「A에게 맞는 후보」를 고르지 「서로에게 맞는 짝」을 고르지 않는다.

검증은 시드가 아니라 **실제 게시 프로필 69건**(`some_us_love_profiles.json`, @some_us.love)으로 했다.

## 2. 지금 무엇이 깨져 있나

전부 코드에서 확인한 사실이다. 데이터와 무관하게 성립한다.

| # | 문제 | 위치 |
|---|---|---|
| 1 | **성별 필터가 없다.** `gender`가 슬라이스에만 있고 필터에서 안 쓰인다 | `web/src/lib/match/filter.ts` |
| 2 | **LLM 랭킹이 단방향이다.** 프롬프트가 「subject에게 어울리는 후보」, `score`도 하나 | `web/src/lib/llm/match.ts` |
| 3 | **데알브레이커가 오탈락만 한다.** 부분문자열이라 「비흡연자」가 「흡연」에 걸린다. 흡연자는 자기 어필에 「흡연」이라 안 쓰므로 정탈락은 불가능 | `filter.ts` `dealBreakerHit` |
| 4 | **`/apply`가 나이 조건을 버린다.** 「위로 2살」을 받지만 `partnerBirthYearMin/Max`에 넣지 않는다. 둘 다 null이면 `birthYearInRange`가 통과시키므로 웹 신청자는 나이 필터를 무조건 통과한다 | `web/src/app/api/public/apply/route.ts` |
| 5 | **`seq`가 매칭 슬라이스에 없다.** 그래서 DM 초안이 상대를 핸들로 지칭한다 — 「핸들은 공개하지 않는다」와 충돌 | `service.ts` `SELECT_SLICE` |
| 6 | **이미 판정한 짝이 다시 추천된다.** 재추천 방지가 없다 | `filter.ts` |
| 7 | **사진이 매칭에 안 들어간다.** 작문 단계는 같은 사진을 비전으로 보는데 매칭만 안 본다 | `llm/match.ts` `sliceForPrompt` |

## 3. 실데이터가 말하는 것 (69건)

| 항목 | 값 |
|---|---|
| 성별 | 여 38 / 남 31 — 균형 |
| `partnerBirthYearMin/Max` 채움 | **23%** (16/69) |
| `partnerAgeRaw`(「위로 2살」) 채움 | **100%** |
| `faceType`(본인 얼굴상) 채움 | **97%** — 스키마에 필드가 없다 |
| 이상형에 **키** 언급 | **94%** |
| 이상형에 성격 언급 | 65% |
| 이상형에 **얼굴상** 언급 | **47%** — 어휘가 닫혀 있다(토끼·강아지·여우·두부·곰·고양이·사슴·다람쥐…) |
| 이상형에 직업 / 체형 언급 | 2% / 7% |
| `dealBreakers` | 흡연 37 · 문신+타투 18 · 음주 12 · 이성문제 6 |

사람들이 실제로 따지는 건 **키 · 성격 · 얼굴상**이고, 절대 안 되는 건 **흡연 · 문신 · 음주**다. 셋 다 이분법이고 검증 가능하다. 그리고 셋 다 필드가 없다.

### 3.1 필터 강도 시뮬레이션

`partnerAgeRaw`를 파싱해 나이 구간을 채운 뒤, 하드필터 강도를 바꿔가며 69명 전원에 대해 후보 수를 셌다.

| 필터 | 후보 중앙값 | 후보 0명 |
|---|---|---|
| 경계만 (이성 + 나이 상호) | **23명** | 1/69 (1%) |
| 선호까지 하드 (+키 +얼굴상) | 5명 | 5/69 (7%) |

**키·얼굴상을 하드필터로 올리면 중앙값이 23→5로 무너진다.** 점수로 둬야 한다.

## 4. 점수 모델

원칙: **경계는 하드필터, 선호는 점수.** 지금은 반대로 되어 있다 — 나이·지역이 하드필터고 진짜 경계인 성별은 필터에 없다.

### 4.1 하드필터 (탈락)

- 자기 자신
- `status ∉ {APPROVED, PUBLISHED}`
- **성별이 같으면 탈락** (신규 — 이성 고정, 운영자 결정). 둘 다 알 때만 판단하고 모르면 막지 않는다 — 성별 미기재를 이유로 프로필이 영영 안 보이면 조용히 사라진다
- **나이 구간 상호, 단 ±2년 여유** (§4.1.1). 채움률은 §5.2로 23%→84%로 오른다
- **이미 판정한 짝** (신규 — 방향 무관. `MatchSuggestion ⋈ MatchRun` 쿼리로 충분, 테이블 추가 불필요)
- **구조화된 데알브레이커만** — 흡연·문신·음주 필드가 생긴 뒤. 자유텍스트 부분문자열 매칭은 제거한다(§2-3)

**지역은 여기 없다.** 점수로만 쓴다(§4.2). 하드필터로 두면 지방 신청자가 수도권 전원에게서 전멸한다 — 실측에서 부산 남성 한 명의 후보가 4명에서 1명으로 줄었다.

### 4.1.1 나이 게이트의 여유 (구현하며 정한 값)

적어낸 나이 구간 밖으로 **2년까지는 게이트를 통과시킨다** (`AGE_GATE_SLACK = 2`).

근거는 실측이다. 실데이터 69건에서 **나이로 탈락한 쌍 1,008개 중 520개가 2년 이내 차이**였다. 절반 이상이 아슬아슬하게 빗나가 통째로 사라지고 있었다. 키에서 1cm 차이를 0점으로 만들지 않으려고 감쇠를 넣어놓고 나이는 1년 차이로 죽이던, 같은 실수였다.

**여유는 게이트에만 준다.** 점수는 적어낸 구간 그대로 깎으므로(6년에 걸쳐 감쇠) 통과해도 뒤로 밀리고, 화면에는 ✕와 함께 상대의 실제 나이가 뜬다. 운영자가 「1년 벗어났다」를 보고 판단하지 시스템이 대신 숨기지 않는다.

실데이터 69건 기준 누적 효과:

| | 후보 중앙값 | 최소 | 후보 0명 |
|---|---|---|---|
| 지역이 하드필터일 때 | 21 | 0 | 1명 |
| 지역을 점수로 | 21 | 2 | 1명 |
| **+ 나이 2년 여유** | **27** | **4** | **0명** |

### 4.2 점수 (감점, 탈락 아님)

방향별로 0~1을 계산한다. `s(A→B)` = B가 A의 조건에 맞는 정도.

| 차원 | 가중치 | 미충족 시 |
|---|---|---|
| 나이 | .30 | 구간 밖으로 벗어난 햇수에 비례 감쇠 |
| 키 | .30 | 벗어난 cm에 비례 감쇠 |
| 얼굴상 | .20 | 원하는 집합과 교집합 없으면 0.25 |
| 지역 | .20 | 교집합 없으면 0.2 |

**미상은 감점이 아니라 중립(0.6)으로 두고 화면에 별도 표시한다.** 조용히 통과시키면 「맞는다」와 「모른다」가 구분되지 않는다.

나이는 게이트와 유사도를 분리한다. `birthYearInRange`는 in/out만 하는데, RECON이 스스로 꼽은 약점 1번이 나이 구간화다(24세와 25세가 다른 버킷이면 비유사). 게이트는 그대로 두고 점수용 등급 거리를 따로 둔다: `Q = (v* − |Δ|) / v*`.

### 4.3 상호 결합 — 조화평균

```
s_pair = 2 · s(A→B) · s(B→A) / ( s(A→B) + s(B→A) )       (한쪽이 0이면 0)
```

RECON (Pizzato et al., RecSys '10)의 알고리즘 그대로다. 산술평균은 **지나치게 낙관적**(한쪽 열의가 무관심을 구제), 기하평균은 **지나치게 비관적**, 조화평균은 최솟값에 가까워 「양쪽 다 충분히 관심 있어야 한다」는 요건을 반영한다. 보고된 효과: top-10 성공률 23% → 42%.

**정렬만 조화평균으로 하고, UI에서는 두 방향 점수를 합치지 않는다.** 비대칭 자체가 운영자에게 정보다. 실데이터 상위 10 후보 중 **16%가 gap ≥ .18**(한쪽만 맞는 짝)이다.

### 4.4 이상형 자유텍스트의 취급

문헌은 자기신고 선호를 일관되게 깎는다. Joel·Eastwick·Finkel 2017(181개 예측변수, 랜덤포레스트)은 관계별 호감도 분산을 **−0.18% / +1.34%** 설명했다 — 평균으로 찍는 것보다 못하다.

다만 그 연구가 잰 것은 **「만난 뒤 끌렸는가」**이고, 우리 KPI는 **「B가 소개 DM에 예라고 했는가」**다. B는 번호 게시물과 자기 기준으로 판단하므로 자기신고 선호가 우리 결과는 더 잘 예측할 수 있다. 문헌을 그대로 적용하지 않는다.

절충: **파싱된 구조화 값(키 구간, 얼굴상 집합)은 점수로 쓰고, 자유텍스트는 tie-breaker로 강등한다.** 실제 가중치는 §7의 결과 로그로 정한다.

반대로 **데알브레이커는 무겁게** 둔다. Jonason et al. 2015(N>6,500)에 따르면 사람은 dealbreaker를 dealmaker보다 더 무겁게 치며, 특히 **첫 접촉 단계**에서 그렇다. 우리가 있는 자리가 거기다.

## 5. 추가할 필드

원칙: 설문을 길게 늘리지 않고 **경계형(이분법·검증가능) 필드만** 추가한다.

### 5.1 스키마 변경

```prisma
model Profile {
  // 신규 — 실데이터 97%가 이미 갖고 있는데 버려지던 값
  faceType            String?
  partnerFaceTypes    String[]

  // 신규 — 이상형 언급률 1위(94%)인데 문자열로 뭉개지던 값
  partnerHeightMin    Int?
  partnerHeightMax    Int?

  // 신규 — 데알브레이커 1·2·3위. 3-state: true / false / null(미상)
  smoking             Boolean?
  tattoo              Boolean?
  drinking            Boolean?
}
```

**넣지 않는 것:** MBTI, 종교, 연봉, 취미 체크박스. 이상형 언급률이 직업 2% · 체형 7%다. 응답 부담 대비 예측력이 낮고, 작은 풀에서 필터로 쓰면 0건이 난다.

### 5.2 스키마 변경 없이 채우는 것

`partnerAgeRaw`(「위로 2살, 아래로 3살」)를 정규식으로 파싱해 기존 `partnerBirthYearMin/Max`에 넣는다. 년생은 작을수록 연상이므로:

```
partnerBirthYearMin = birthYear − 위로N       (연상 한계)
partnerBirthYearMax = birthYear + 아래로M     (연하 한계)
```

실데이터 검증: **16 → 58/69 (23% → 84%)**. 스키마 변경 없이 기존 필드를 채우는 것뿐이다.

`/apply` 라우트도 같은 변환을 해야 한다(§2-4). 신청 시점에 본인 `birthYear`를 알므로 서버에서 계산 가능하다.

## 6. LLM 호출 구조

지금은 후보 30명을 한 번에 넣고 subject 기준으로 랭킹하니 subject에 anchoring된다.

바꿀 것:

1. **구조화 필드로 먼저 결정적 사전랭킹** — LLM 없이, 즉시, 무료
2. **상위 8명만 LLM에**, 각 후보의 이상형을 함께 넣고 **두 방향 점수를 따로** 받는다
3. **사진을 슬라이스에 포함** — 외모가 호감을 예측하는 효과가 메타분석(k=97) 기준 r ≈ .40, 남녀 동일. 경제력(r ≈ .10)의 4배다. 작문 단계는 이미 같은 사진을 본다
4. `seq`를 `SELECT_SLICE`에 추가하고 프롬프트를 「핸들은 @로 표기」에서 **「번호로 지칭」**으로 바꾼다

호출은 1회 유지, 비용은 오히려 감소한다.

### 6.1 프롬프트에 추가할 금지 조항

`MATCH_SYSTEM`에는 「없는 사실 지어내지 마라」는 있지만 **「상대의 선별 기준을 누설하지 마라」가 없다.**

- ❌ 「그쪽은 님 직업 괜찮대요」 → A가 직업을 따진다는 사실이 노출됨
- ✅ 「둘 다 진지한 만남을 원하신다고 하셨어요」 → 양쪽이 자발적으로 밝힌 것만

Nissenbaum의 contextual integrity 기준이다. A가 **운영자에게 선별 목적으로** 준 정보를 B에게 넘기면 비밀이 새지 않아도 침해다.

반대로 **양쪽 이유를 함께 설명하는 것은 우리 경우 맞다.** Kleinerman et al. RecSys '18(287명): 수락에 비용이 클 때는 상호 설명이 낫고, 비용이 없으면 오히려 나쁘다. 사람이 직접 보내는 소개 DM은 비용이 큰 쪽이다.

## 7. 데이터 축적 레이어

원칙: **append-only 이벤트 + 주기 스냅샷. status 컬럼을 늘리지 않는다.**

이벤트로 두는 이유: ① 미래 신호 종류를 모른다 — `kind`만 추가하면 된다 ② status는 덮어쓰기라 이력이 사라진다 ③ 이벤트→상태는 계산되지만 역방향은 안 된다.

### 7.1 `PostMetric` — 주기 스냅샷

```prisma
model PostMetric {
  id         String   @id @default(cuid())
  profileId  String
  likes      Int
  replies    Int
  reposts    Int
  quotes     Int
  capturedAt DateTime
}
```

`GET https://graph.threads.net/v1.0/{media-id}/insights?metric=likes,replies,reposts,quotes`

- `Profile.publishedPostId`가 이미 저장돼 있어 바로 붙는다
- **`threads_manage_insights` 스코프가 필요한데 현재 `SCOPES`에 없다 → 재연결 1회 필요.** `client.ts`의 주석이 이 제약을 이미 문서화하고 있다
- `period=lifetime` 누적값이라 스냅샷을 쌓아야 증가분이 나온다. **총 좋아요보다 초기 24h 증가 속도**가 인기 신호로 유용하다

### 7.2 `MatchFeedback` — 이산 이벤트

```prisma
model MatchFeedback {
  id            String   @id @default(cuid())
  actorId       String            // 누가
  counterpartId String            // 누구를
  kind          FeedbackKind      // DECLINED / ACCEPTED / NO_REPLY / WITHDRAWN
  reasonCode    String?           // 닫힌 집합, 1클릭
  reasonText    String?  @db.Text // 원문 병기 — 원본 보존 원칙
  source        String            // OPERATOR / DM / WEB
  observedAt    DateTime          // 관측 시각 (기록 시각과 분리)
  createdAt     DateTime @default(now())
}
```

**방향이 핵심이다.** 「B가 A를 거절」 = `(actorId=B, counterpartId=A)`. 지금 `MatchSuggestion.status = DISMISSED`는 **운영자가 버린 건지 당사자가 거절한 건지 구분이 안 된다** — 가장 중요한 신호가 소실되고 있다.

`reasonCode`를 닫힌 집합으로 두는 근거: 전문 중매인들은 거절 사유를 **당사자에게 전달하지 않으면서도** 집요하게 캐낸다. 「'내 타입이 아니다' 같은 일반적 답변은 검색 조건을 좁히는 데 도움이 안 된다. 어떻게 타입이 아니었는지 — 외모인지, 태도인지, 관심사인지 말해달라」(The Matchmaking Company). 사유 분류는 그 실무를 그대로 옮긴 것이다.

### 7.3 신호가 매칭에 돌아오는 3경로

1. **혼잡 제어** — §8
2. **드러난 선호** — A가 실제로 수락/거절한 사람들의 공통점. 69건 규모에선 모델을 못 만들지만, **운영자에게 「A가 거절한 3명의 공통점」을 보여주는 건 지금도 가능**하다
3. **거절 사유 → 가중치 조정** — 「사진이 취향 아님」이 지배적이면 필드 매칭을 아무리 잘해도 소용없다. 「거리」가 지배적이면 지역 가중치를 올린다. §4.4의 열린 질문을 답하는 유일한 방법

## 8. 혼잡 제어

실데이터에서 **한 사람이 최대 16명의 상위5에 등장한다.**

인기 있는 사람에게 추천이 몰리면 그 사람이 답할 수 있는 양을 넘어선다. RECON이 스스로 꼽은 약점 2번이고, 후속 연구는 노출 분산이 공정성이 아니라 **성사 총량**의 문제라고 말한다(Tomita et al., RecSys '23). 혼자 DM 보내는 운영자에게는 그대로 병목이 된다.

구현: 「한 사람이 동시에 열려 있는 추천 N건을 넘지 않는다」 상한. 넘으면 랭킹에서 감점하고 화면에 표시한다.

## 9. 화면 — 짝 대조 시트

`/impeccable redesign` 라운드에서 확정(seed `2f1c28d4`, 운영자가 3개 중 선택).

시안: `docs/superpowers/specs/2026-08-15-matching-facing.html`. **`__DATA__` 자리에 프로필 JSON을 끼워 넣으면 실행되는 템플릿**이다 — 실데이터를 박은 빌드본은 저장소에 넣지 않는다(§12).

- **한 번에 한 짝.** 소개받는 분과 후보를 두 장의 종이 카드로 마주 놓고, 가운데 홈이 맞물림을 잇는다. 위 레일로 후보를 넘긴다(`←` `→` 키 지원)
- **점수 대신 판정 문장.** 「서로 잘 맞아요」 / 「한쪽만 맞아요」 / 「무난해요」. 숫자는 홈과 접기 안으로
- **조건 줄마다 충족 표시.** 채운 도장 ✓ / 빈 도장 ✕ / 점선 미상, 그리고 **옆에 상대의 실제 값**(「62번 162cm」). 안 맞는 줄은 요구치를 흐리게, 실제 값을 진하게
- **작업목록.** 물어봄 / 승낙 받음 / 거절. 거절하면 접히고 다시 안 올라온다. 한 명 성사까지 다섯에서 열 명에게 물어보는 실무를 전제로 한다
- **폰.** 기준 카드가 접히고 요약 마크만 남으며, 동작 버튼이 하단 고정

시각 월드는 기존 Some Love Admin을 유지한다. 이번 라운드에서 `DESIGN.md`에 올린 것은 **면별 사람 색 쌍**과 **status-seal 규칙** 두 가지뿐이다. 맞물림 마크는 양방향 점수가 있는 화면에서만 뜻이 있으므로 서피스 브리프에만 기록했다.

## 12. 범위 밖 / 미해결

- **DM 발송·공개 순서** — 운영자 결정으로 보류. 순차(한쪽 먼저 물어보고 OK면 반대쪽) vs 동시는 미결. 참고로 인바운드 `Inquiry` 파이프라인은 순차인데 `acceptSuggestion`은 동시라, 같은 운영자가 두 철학을 쓰고 있다
- **쌍은 한 방향으로만 제안** — KDD '24는 한쪽에 추천해 성사되면 반대쪽 추천은 redundant라고 지적한다. 지금 `acceptSuggestion`은 `DeliveryItem` 2건을 만든다. DM 설계와 함께 다룬다
- **성별을 이성으로 하드코딩** — 확장하려면 `seekingGender` 필드와 마이그레이션이 필요하다
- **화면이 아직 앱에 붙지 않았다** — 독립 HTML 시안이다. 붙이려면 §4~6이 먼저다
- **개인정보** — 익명화 재작성 게시는 제3자 제공과 다르다는 운영자 판단. 다만 실제로 두 사람을 연결하는 CONNECT 단계는 성격이 다르므로 그때 다시 본다
- **성격 정합** — 이상형 언급률 2위(65%)인데 구조화 계획이 없다. 자유텍스트 tie-breaker로만 쓴다
- **실데이터 파일의 버전관리** — `some_us_love_profiles.json/yaml`은 실존 인물 69명의 프로필이라 저장소에 커밋하지 않았다. 시안 템플릿과 이 문서의 통계만 남긴다. 버전관리가 필요하면 `.gitignore` 처리 여부를 먼저 정해야 한다
